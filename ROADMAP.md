# Roadmap

What is done and what is next, in the order to do it, as of 2026-11-17. Plan and decisions: `docs/ARCHITECTURE.md`; research:
`docs/fm-1_reference-kit.md`, `docs/HARDWARE.md`. **The five bundled firmwares boot and play on a Mac**, but **nothing has run on a real FM-1**, and on the one R36S
measured (2026-11-17) the core is far too slow to play live (**0.24x real time at the best setting in steady state**, JIT with pacing, goal 1x; section 1). Section 6b (fm1tastik) Phase 1 is **live**.

## 1. Make firmware run

- [x] **CPU route decided** (maintainer, 2026-11-16): vendor `fm1-emu`'s core, with a `NOTICE` line.
- [x] **Vendored** (`core/vendor/fm1-emu`, commit `60645a5`, 2026-11-15): `fm1-isa`, `fm1-core` (the pi32v2 interpreter and its native block compiler), `fm1-soc` (map, LCD, flash, audio, USB, the `.fwsc` reader), the licence, `VENDORED.md`, and a `NOTICE` line. Only the workspace's `members` is changed.
- [x] **The machine** (`core/src/machine.rs`): boots a `.fwsc` package or a raw XIP image, renders audio paced by the caller, reads the screen, takes keys, encoders, the pot and MIDI bytes; deterministic; 8 tests (refusals, bounds, a garbage image halting safely, the same input giving the same frames).
- [x] **First real boot** (2026-11-16, on this Mac, from the bundled firmware): **all five Haunted FM-1 v0.1 packages boot and draw their own screen** (55-75 distinct colours each), UNTRUE STEP runs at 1.00x with its drum grid moving and **makes sound** (a recorded demo: peak 12,561 of 32,768), the keys and buttons are driven through the real input path. A real firmware found a bug the synthetic tests could not: **restoring a saved flash halted the machine** (the whole saved flash was copied over the execute-in-place view, replacing the decrypted app with encrypted bytes); fixed to write only the sectors that differ, with a regression test on a real firmware.
- [x] **The stock firmware runs** (2026-11-18, the maintainer's `docs/FM-1.fwsc`, local only; `docs/HARDWARE.md`): it boots, draws the screens the manual describes, and EDIT's black keys select OP1-OP6, PIT and GLO in the order assumed. [ ] **Which other firmwares run** (Felucca, SLOOP, Melodee, S1Vave...): they are GPL or closed and not bundled; the maintainer runs them locally and reports here.
- [x] **Speed on this Mac (Apple M1), WORN TAPE** (`--bench --fw`): the interpreter 0.90x real time, **the native JIT 5.12x** (the JIT engages on real firmware code, though not on the nop loop). **The R36S's Cortex-A35 is several times slower than an M1, so the interpreter will not keep up there and the JIT is the route** (`fm1ntt_jit`, off by default: it writes executable memory, so check the 4.4 vendor kernel allows it, and make it the default where it works). [x] **First R36S figures (device report 2026-11-17, UNTRUE STEP):** interpreter **0.03x** real time, native JIT **0.22x**; both FAIL the 1x goal (the nop loop is 1.6 Minsn/s either way). [x] **Investigation done** (`docs/PERFORMANCE.md`): the unit is ~15-25x slower than an M1, all nine firmwares tried keep the CPU ~98% busy, the JIT is on by default now, and main-loop pacing (AUTO) is built (Mac: 1.4-4.5x; projection for the unit ~0.45x). [ ] **Bundled firmware not listed on the unit (maintainer, 2026-11-17):** lookup made robust and the report says where it looked; [ ] rebuild the package, run the Device report and read the `program folder`, `bundled firmware` and `firmware pack` lines (the cause is unknown until then). [ ] **Run the new report and benchmark on the unit** (`best setting` line, and the clock lines), and listen: pacing is untested by ear and on the unit. [x] **A faster JIT, first part** (2026-11-17, recorded in `VENDORED.md`): 14-18% fewer host instructions per guest instruction (register ops and compares on the held host registers, address from the operand, a cheaper range check); the then-part of a plain `if { }` in line was tried: no gain. [ ] **Send the JIT change upstream** (a pull request to `joakimeriksson/fm1-emu`). [ ] **The structural rest** (guest registers kept in host registers across chained blocks, a cheaper block entry, longer blocks): perhaps another 15%, a rewrite of the compiler's block model; measure the first part on the unit before starting it. [x] Native replacement of the interrupt handlers' hot routines: profiled (flat, per firmware, little shared code), not worth building (`docs/PERFORMANCE.md`). [ ] Teach `probe_loop` the SPI-busy poll loops (exact idle skip). [ ] Try `lto = "fat"` and `codegen-units = 1` for the core (measure on the unit). [x] **Steady-state figures (benchmark workload 2, R36S, 2026-11-17, UNTRUE STEP after a warm-up past its boot):** interpreter 0.036x, JIT 0.177x, JIT paced 1/2/3 0.240x/0.233x/0.241x; the earlier 0.29x, 0.64x and 1.37x timed the cheap start (`docs/PERFORMANCE.md`). The gap to 1x is about 4x. [x] `lto = "fat"` + `codegen-units = 1` tried on the Mac: no gain, dropped. [x] **The Device report's firmware lines use the same warm-up** (built 2026-11-17; not run on the unit). [x] **Counters for where the unit's time goes** are in the benchmark file (`# jit` lines, built 2026-11-17; Mac: 99.4% of guest instructions run compiled, the window still compiled 1,443 blocks). [x] **Benchmark run on the unit and the `# jit` lines read (2026-11-18, build 53d4504; `docs/PERFORMANCE.md`):** 99.9% of guest instructions run compiled and the window compiled about 240 blocks, so compile time is not the cost; figures unchanged from 2026-11-17 (JIT 0.185x, pace 3 0.246x). [ ] **What is left is how fast the A35 runs the compiled code** (block entry/exit against memory stalls); the JIT's own `# jit` lines cannot tell them apart, so measure with `perf` if the unit has it, or by changing one (the interrupt-delivery path) before starting the structural work: the original line follows. the A35 runs the JIT at an IPC near 0.3, and compile time, block entry/exit and memory stalls each point at a different fix. [ ] **The structural JIT work** (guest registers in host registers across chained blocks, a cheaper block entry, longer blocks; `docs/PERFORMANCE.md`): needed for the 4x, and each part is worth about 1.1-1.3x, so it will not get there alone. [x] **What the R36S is for if 1x does not come:** **Decided 2026-11-18 (maintainer confirmed):** a sound instrument first (Solo and `.fm1i` ports), recorded demos to hear firmware, the Mac and web builds as the live emulator; no promise of live firmware on the unit. [x] **Second part of the JIT** (2026-11-17, `VENDORED.md`, `docs/PERFORMANCE.md`): 5-7% fewer host instructions per guest instruction (a block's budget taken off once at its entry, float ops and immediates on the held registers, cold code after the hot code); identical to the interpreter on nine firmwares; **measured on the unit (2026-11-17): +4.4% unpaced (0.1781x to 0.1859x), +5.5% at pace 3 (0.2349x to 0.2478x); the cold-code layout added nothing visible**. [ ] What is left in the JIT (`docs/PERFORMANCE.md`): a compiled path for interrupt delivery (83% of the exits to Rust are an interrupt becoming deliverable), guest registers across chained blocks, loads and stores with their slow path out of line: perhaps 1.3x together, not 4x. [x] **Firmware audit for the R36S** (2026-11-17, `docs/R36S-FIRMWARE.md`, `r36s/firmware-audit.tsv`): 195 firmwares measured; **two files (Compás) are predicted to keep up, six are borderline, none of the nine FM1-NTT ships gets above 0.5x** (an estimate from one calibration point; nothing played on a unit). [x] **Compás is not bundled** (maintainer, 2026-11-17: it embeds CC BY-SA 3.0 / CC BY data, a portrait and recordings outside the pack's allowlist; on the watchlist with the reasons). [ ] **Try Compás on a unit** (downloaded from its release, `--report FILE`) and measure it with the Device report: that turns the prediction into a number. [ ] Ask the Compás author whether the data can be separated from the firmware. [x] **Decided 2026-11-18 (maintainer confirmed):** the allowlist is **not** widened to CC BY / CC BY-SA; Compás stays on the watchlist. [ ] The 96 repositories with no release `.fwsc`, and the closed-source firmwares, were not audited. [ ] The core is far too slow on the Cortex-A35 to run firmware live: profile the JIT's engagement on aarch64 and the interpreter's hot path, or lower the emulated work (idle skip), before any claim of playing on the unit.
- [x] **Using the other cores, looked at** (maintainer, 2026-11-17; `docs/PERFORMANCE.md`): the machine runs on one host thread, two of four cores idle. **Built: CPU time by thread** in the Device report (`threads`) and the benchmark (`# threads`), **the free-against-pinned placement test** (`thread placement`, `# thread placement`; TOOLS only), and **`--pin` / `FM1NTT_PIN=1`** (off by default). Linux, Debian 12 arm64 in Docker: self-test and the end-to-end test pass. [x] **Run on the unit (2026-11-18):** the emulating thread uses 100.0% of one core (cpu 1), the main thread 3.7%, audio 1.5%, all 17 threads 106.2% of 4 cores; **pinned 0.246x against free 0.249x, ranges overlap: no difference, so `--pin` stays off.** The main thread is already apart, so the cores are not the limit; only the two-thread split (non-deterministic, a spike in a scratch copy) is left for them. [ ] Then, by what the threads show: a JIT tier compiled on a spare core, or the spike that splits the main loop from the interrupt handlers across two threads (non-deterministic, a separate fast mode; scratch copy first).
- [ ] **Even pacing** of the emulation per audio buffer (upstream's `Pace` in `fm1-web`): today each buffer runs what it needs, which spikes for firmwares that make audio in big half-buffers.
